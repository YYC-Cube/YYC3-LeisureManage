## 一、文档定位

本目录是 **YYC³ LeisureManage 多环境闭环提示词体系的唯一入口**，回答三个问题：

1. **在哪个环境、哪个端、哪个阶段**——用哪一条提示词；
2. **提示词如何约束 AI**——必须读什么、必须证什么、必须交什么；
3. **一次闭环如何结束、如何交给下一个环境**——闭环卡与 `next-hook` 契约。

本体系不是"提示词范文合集"，而是**可被 AI 反复加载、自我校验、跨环境传递的运行时契约**。文件即结构，结构即约束，约束即闭环。

### 1.1 本体系解决的问题

| 现状痛点 | 典型表现 | 本体系对策 |
| -------- | -------- | ---------- |
| 环境漂移 | 本地能跑、预发报错、生产回滚；端口/域名/变量各说各话 | 环境契约先行（`YYC3-环境契约-环境矩阵与准入门禁`） |
| 口径不一 | 每个会话各自发明"验收通过"的标准 | 统一闭环卡 + 统一 P0/P1/P2 分级 + 统一 DoD |
| 会话断裂 | 长会话上下文丢失，下一次重新问"你想做什么" | 三层记忆协议 + `next-hook` 强制字段 |
| 空想式回答 | 不读代码直接给方案，结论不可证 | 证据优先思考协议：无证据不结论 |
| 工具闲置 | 明明有技能/工具，却靠猜 | 主动技能路由表：触发条件 + 禁用边界 |
| 交付不闭环 | 代码改了、文档没写、观测没做 | 七段闭环：准入→执行→验证→裁决→记忆→挂钩→归档 |

### 1.2 本体系不做什么

- 不替代《YYC³ 团队通用-开发标准》《YYC³ 团队通用-命名规范》《YYC³ 团队通用-标头标尾》——本体系全部文档服从上述强制规范；
- 不替代《YYC³ 项目闭环-验收系统》的 13 阶段验收条款——本体系负责"如何提问、如何裁决、如何交接"，验收条款以验收系统为准；
- 不承诺不存在的事实。仓库无 Next.js 应用时，不把 Next.js 规则当作现网事实（见 §十二 技术栈事实校正）。

## 二、双轴模型：环境轴 × 端轴

"多环境"在本体系中同时指**部署环境**与**运行端形态**，二者必须交叉定位，禁止只报环境不报端。

### 2.1 环境轴（E0 → E5）

| 代号 | 环境 | 入口 | 关键事实（以现网为准） |
| ---- | ---- | ---- | ---------------------- |
| **E0** | 本地开发 | 开发者工作站 | Web dev 端口 3040、API dev 3001、开发库 5434、Redis 6380；规则要求开发服务器 3030 起 |
| **E1** | 集成构建 | GitHub Actions | `ci.yml` / `release.yml`；`scripts/verify-gates.sh` G1–G6；mock 审计、i18n 裸键、复用率 |
| **E2** | 预发联调 | 预发静态目录 / NAS 备实例 | 双 API 实例：Mac 主 3002（frp 8802）、NAS 备 3001（frp 8801）；ECS 边缘 nginx |
| **E3** | 生产运行 | <https://lm.0379.world> · <https://lm.0379.pro> | Web 静态 `web/`、销售端 H5 `h5/`、微信小程序、PG15 主库 5433、Redis、审计与对账 |
| **E4** | 灾备回退 | NAS 备库 / 旧版本产物 | RTO ≤ 15 分钟、RPO ≤ 24 小时；切流 8802↔8801；迁移只加列 |
| **E5** | 归档复盘 | 文档与台账 | 闭环卡、验收报告、`next-hook` 写入记忆；文档闭环与知识资产沉淀 |

### 2.2 端轴（T1 → T5）

| 代号 | 端 | 技术事实 | 主要约束 |
| ---- | -- | -------- | -------- |
| **T1** | Web 管理端 | React 19 + Vite 8 + React Router 7 + Tailwind 4 + zustand + `@yyc3/ui` | Vite 构建、`dist/` 静态发布、同源 `/api/v1` |
| **T2** | 销售端 H5 | Taro 4 + React 18，`build:h5` | `TARO_APP_API_BASE` 编译期内联，改域名必须重构建 |
| **T3** | 微信小程序 | Taro 4 `build:weapp` | 合法域名、构建产物与 H5 同源逻辑 |
| **T4** | API 服务 | NestJS 10 + Prisma 5 + PG15 + Redis | 全局前缀 `/api/v1`；生产硬化校验；受限账号 |
| **T5** | 领域核心包 | `@yyc3/leisure-core`（框架无关单源） | Web 与 Taro 共用；业务计算不得在端内分叉 |

### 2.3 定位写法（强制）

任何一次会话、任何一份闭环卡，开头必须声明：

```
【环境】E2 预发联调
【端】T1 Web 管理端 + T4 API 服务
【阶段】verify（验证）
【基线】commit <sha> / tag <v> / 产物 <路径>
```

缺任一维度，视为**定位不完整**，不得进入执行。

## 三、七段闭环定义

一次"闭环"不是"做完一件事"，而是七个段落全部有产物。缺段即未闭环。

```
① 准入 Entry       —— 环境契约、基线、权限、密钥来源已确认
② 执行 Execute     —— 按计划实施，最小改动，过程留痕
③ 验证 Verify      —— 命令级证据 + 关键路径自检 + 回归
④ 裁决 Verdict     —— PASS / CONDITIONAL / BLOCK，附 P0/P1/P2
⑤ 记忆 Memory      —— 锁定层 / 会话层 / 状态层按规则写入
⑥ 挂钩 Hook        —— next-hook：下一环境、第一动作、必带记忆、重建顺序
⑦ 归档 Archive     —— 闭环卡、报告、台账、文档同步
```

> **闭环判据**：能回答"证据在哪、偏差多少、下次从哪开始"三问，才算闭环。

## 五、统一提示词骨架（九段式）

所有环境环的提示词都必须收敛到同一骨架，便于 AI 稳定加载、便于人工审计。

```text
【0 角色】你是谁：YYC³ 的什么角色，服务于哪个环境/端，遵循五高五标五化五维。
【1 上下文】项目、环境、端、阶段、基线（commit/tag/产物）、已锁定记忆、上次 next-hook。
【2 目标】本次唯一目标（一句话）+ 非目标（明确不做什么）。
【3 约束】硬约束（不可协商）/ 软约束（可协商）/ 红线（触碰即停）。
【4 思考协议】证据优先：先采集事实，再提假设（≤3），再做反证，最后裁决并标置信度。
【5 技能路由】本环境应主动加载的 Skill / MCP 工具，触发条件与禁用边界。
【6 动作】编号步骤，每步声明"读什么、改什么、跑什么、产出什么"。
【7 输出】闭环卡 YAML + 报告正文 + 证据清单 + 待确认项 + next-hook。
【8 自检】DoD 清单逐条打勾；未完成项必须写原因与补救动作。
```

### 5.1 会话格式三型

| 类型 | 适用 | 结构 | 时间盒 |
| ---- | ---- | ---- | ------ |
| **速诊型** | 单点问题、快速判断 | 定位 → 证据（≤3 条）→ 结论 → 下一步 | ≤ 10 分钟 |
| **标准型** | 一次完整环境闭环 | 九段式全量 | 30–90 分钟 |
| **续接型** | 跨会话/跨日 | 上次 next-hook → 记忆核对 → 现状校验 → 本次第一动作 | ≤ 5 分钟完成衔接 |

> **禁止**：续接型不得从"好的，我来帮你……"开始；必须先完成上下文定位并声明"从哪个阶段继续"。

### 5.2 阶段小结义务

每完成一个阶段（分析完、实现完、验证完），必须输出**压缩小结**：

```
本阶段完成：…
记忆更新：…（写入哪一层、哪个文件）
被推迟：…（原因 + 下次触发条件）
```

## 六、深度思考协议（证据优先）

### 6.1 五步推理

| 步骤 | 要求 | 不合格表现 |
| ---- | ---- | ---------- |
| 1 事实采集 | 读代码、读配置、跑命令、看产物；列"已核实事实" | 凭印象描述项目 |
| 2 假设生成 | 最多 3 条，按可能性排序 | 无限发散、假设当结论 |
| 3 反证检验 | 对首选假设找**一条反证**；找不到才可采纳 | 只找支持证据 |
| 4 影响分析 | 五维：时间/空间/属性/事件/关联 | 只谈功能，不谈回归 |
| 5 裁决标注 | 结论 + 置信度（高/中/低）+ 待确认清单 | 无置信度、无待确认 |

### 6.2 可审计推理摘要格式（输出必带）

```text
【证据】file:line / 命令输出摘要 / 产物路径
【假设】H1 …；H2 …；H3 …
【反证】针对 H1 的反证与结果（成立/不成立）
【裁决】采用 Hx，置信度 高/中/低
【待确认】需人工确认的配置、环境、业务口径
```

### 6.3 硬性禁止

- ❌ 未读目标文件即给出修改方案；
- ❌ 未运行命令即声称"测试通过 / 构建成功"；
- ❌ 用"应该 / 大概 / 一般来说"替代证据；
- ❌ 把未验证的推断写成事实（必须标"待确认"）；
- ❌ 隐藏矛盾证据（矛盾必须显式暴露并解释）。

## 七、主动技能路由

**原则：工具优先于猜测；技能按需加载，不加载不臆造其能力。**

| 代码评审 | MCP `yyc3_code_review` / `yyc3_code_review_enhanced` | 需要结构化评审报告 | 分级问题清单 | 结论须复核证据 |

## 八、技术择优总表（同场景择优）

| 质量门禁 | `verify-gates.sh` + vitest | — | 与 CI 同源 | 本地只跑 build 就宣称通过 |
| 静态发布 | rsync `dist/` 到边缘 | 版本目录切换 | 现网发布流 | 直接改线上文件不保留上一版 |
| 观测 | 日志 + 巡检 + 切流预案 | 新增健康端点（建议） | 现网无独立 health 端点 | 用"看起来正常"代替探测 |

> **条件项**：若未来引入 Next.js 应用，则按 App Router 规则补充 RSC/Client 边界、`"use client"` 最小化、Server Action 鉴权；在引入前不得把 Next.js 规则写成现网事实。

## 九、闭环卡与 next-hook 契约

### 9.1 闭环卡（Loop Card）

```yaml
loop_card:
  loop_id: "LM-{E}-{T}-{YYYYMMDD}-{seq}"
  env: E0 | E1 | E2 | E3 | E4 | E5
  ends: [T1, T2, T3, T4, T5]
  stage: entry | execute | verify | verdict | memory | hook | archive
  baseline: "commit/tag/artifact"
  verdict: PASS | CONDITIONAL | BLOCK
  evidence:
    - cmd: "执行的命令"
      result: "exit code / 关键输出摘要"
      artifact: "path:line 或 产物路径"
  deviations:
    - plan: "计划"
      actual: "实际"
      reason: "偏差原因"
  risks:
    p0: []
    p1: []
    p2: []
  pending_confirmation: []
  memory_writes:
    pinned: []
    session: "YYYY-MM-DD-slug/summary.md"
    state: "current-phase"
  next_hook:
    env: "E1"
    stage: "verify"
    first_action: "可直接执行的第一步"
    required_memory: ["memory/pinned/tech-decisions.md"]
    rebuild_order: ["00", "01", "07"]
```

### 9.2 next-hook 最小字段（缺一即无效）

| 字段 | 含义 | 反例 |
| ---- | ---- | ---- |
| `env` / `stage` | 下一环境与阶段 | 只写"继续开发" |
| `first_action` | 下一次第一条可执行动作 | "再看看" |
| `required_memory` | 必带记忆槽位（具体路径） | "带上之前的上下文" |
| `rebuild_order` | 上下文丢失时的读取顺序 | 无 |

### 9.3 三层记忆

| 记忆层 | 位置 | 内容 | 注入时机 |
| ------ | ---- | ---- | -------- |
| 锁定层 | 项目级 pinned 记忆 | 技术决策、环境契约、用户偏好、待决问题 | 每次 kickoff 全量注入 |
| 会话层 | `YYYY-MM-DD-slug/summary.md` | 单次会话压缩小结 | kickoff 注入最近 1–2 条 |
| 状态层 | `current-phase` | 当前环境/阶段指针 | 每轮轻量注入 |

**不变量**：锁定层不得被会话层摘要覆盖；记忆指纹变化必须触发人工确认（详见 07 号文档）。

## 十、提示词质量评估量表

用于评估任一提示词文档是否达到"教科书级"，每项 0–10 分，总分 100。

| 维度 | 评估问题 | 满分标准 |
| ---- | -------- | -------- |
| 结构完整度 | 九段式是否齐全 | 九段齐全且有编号 |
| 上下文密度 | 是否给出项目事实而非泛泛而谈 | 含端口/路径/命令/约束 |
| 约束刚性 | 硬约束/红线是否可判定 | 有"禁止 + 强制 + 条件"三类 |
| 证据要求 | 是否强制命令级证据 | 要求 cmd + result + artifact |
| 深度思考 | 是否要求假设与反证 | 有推理摘要格式 |
| 技能路由 | 是否声明加载时机 | 有触发与禁用边界 |
| 技术择优 | 是否给出场景化选择 | 有首选/备选/依据/反模式 |
| 可执行性 | 能否直接复制执行 | 提示词块可直接用 |
| 闭环度 | 是否有裁决与 next-hook | 闭环卡字段完整 |
| 演进性 | 是否可评估、可迭代 | 有量表与变更历史 |

**评级**：≥90 教科书级 / 80–89 可投产 / 70–79 需补强 / <70 退回重写。

```
06 观测（判级 L1/L2/L3）→ 01 环境契约（确认切流位）→ 05 回退 → 08 复盘归档
```

## 十二、技术栈事实校正（重要）

本体系以**仓库实际代码**为准，不以外界通用模板为准。经仓库核验：

| 断言 | 事实 | 处理 |
| ---- | ---- | ---- |
| "Web 使用 Next.js App Router" | 仓库中无 Next.js 应用；Web 为 React 19 + Vite 8 + React Router 7 | 不得作为现网事实；Next.js 规则仅作条件项 |
| "shadcn/ui 独立包" | `@yyc3/ui` 为 shadcn/radix 同源 49 件内部包 | 组件规则以 `@yyc3/ui` 为准 |
| "MySQL 主库" | 2026-11-02 已切换 PG15；开发库 5434、生产主库 5433 | 以 PG15 与迁移纪律为准 |
| "单端 Web" | 实为 Web / H5 / 小程序 / API / 核心包五端 | 必须按端轴定位 |

> 该校正同时构成对存量《YYC3-前端闭环验收提示词.md》的评估结论之一（见该文档 §评估结论）。

## 十三、体系不变量

1. 任何提示词必须能定位到 **环境 + 端 + 阶段 + 基线**；
2. 任何结论必须能追溯到 **命令 / 文件:行号 / 产物**；
3. 任何闭环必须产出 **闭环卡 + next-hook**；
4. 任何环境变更必须先过 **环境契约**，不得"先改再补文档"；
5. 任何生产动作必须有 **人工批准** 与 **回退路径**；
6. 任何文档必须符合《YYC³ 团队通用-命名规范》《YYC³ 团队通用-标头标尾》；
7. 任何密钥只出现在密钥库，文档只写变量名与占位符。
